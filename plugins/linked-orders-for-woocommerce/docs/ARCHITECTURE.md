# Architecture

This document describes how the plugin loads, boots, stores its data and leaves a site, and where each kind of code lives.

## Loading

`linked-orders-for-woocommerce.php` is the only file WordPress includes, and it parses on PHP 7.4 so that a site below the floors gets a notice instead of a fatal error:

1. It defines `DWS_LOWC_FILE`; translations come from wordpress.org's language packs, which WordPress loads just in time.
2. It requires `Safeguards.php` and registers its safeguards, an empty slot for restrictions that must hold on any runtime that parses the plugin: below the floors, on a partial deploy and when the boot fails.
3. Inside one `try`, it requires `vendor-prefixed/ahegyes/wp-framework-bootstrap/load.php`, registers the GitHub updater, which stays inert because the entry file has no `Update URI` header, then checks the `Requires PHP` and `Requires at least` headers. The updater comes first, so a release that lowers the floors still reaches a site below them. On a site below a floor, WordPress's own notice shows and nothing past the safeguards loads.
4. It requires the autoloader and `functions.php` once the orders list's built script is present. A missing bootstrap package, build or required file throws, which local and development environments rethrow, while every other environment shows users who can activate plugins a notice that the build is incomplete.

`functions.php` defines the `@api` `dws_lowc_plugin()` accessor, requires every `includes/*.php` in name order except those whose names start with `_`, then, from static closures, boots the plugin on `plugins_loaded` at priority 15, after WooCommerce and Action Scheduler have loaded, declares the plugin compatible with WooCommerce's order tables, relays the framework's boot hooks to v1's `dws_lowc_initialized` and `dws_lowc_initialization_failure` and registers the deactivation callback.

## Booting

`src/Plugin.php` is the composition root. Its constructor builds the plugin's identity from its entry file, slug and prefix, then the logger, the scheduler and the framework's `PluginBoot`, which each take the identity, and `PluginBoot` runs the composition and reports its outcome:

- The scheduler registers its hooks first, so the plugin's scheduled hooks keep their schedules while the plugin is blocked.
- `WooCommerceRequirement` checks WooCommerce against the `WC requires at least` header; without it, the boot is `blocked`, `linked_orders_for_woocommerce/boot/blocked` fires, and users who can activate plugins see why the plugin stays off.
- The migration runner registers, runs pending steps on `wp_loaded`, and runs a batched step's batches from its scheduled hook.
- The kernel builds each class in `Plugin::COMPONENTS` through a PHP-DI container and calls its `register_hooks()`; a composite adds its children, and a conditional component loads only when its static `should_load()` returns true.
- `CapabilityGrants` gives administrators and shop managers v1's four capabilities on `wp_loaded`, once per change of the declaration or the roles.
- Once every component has registered, the boot is `booted` and `linked_orders_for_woocommerce/boot/succeeded` fires. A throw anywhere in the composition makes it `failed`: `linked_orders_for_woocommerce/boot/failed` fires, the failure is logged, and administrators see a notice, while local and development environments rethrow it.

The request that activates the plugin does not boot it, because WordPress includes the plugin's file after `plugins_loaded`; its screens and migrations first run on the next request.

## Where code lives

- `src/` holds the plugin's classes, each final and named for its concept. The components implement the framework's `ComponentInterface` and add their hooks in `register_hooks()`: `Settings` adds the `dws-linked-orders` section to WooCommerce's Advanced tab; `ChildCreation` answers v1's admin-post action; `MetaBox` and `ListTable` add the links to an order's editor and to the orders list, on either order storage, checking the user's capabilities in each callback; `Autocompletion` completes descendants; `OrderDeletion` makes the children of an order deleted for good the roots of their own trees; `Integration\SequentialOrderNumbersPro` loads only beside that plugin. The classes that register no hooks are `Options`, `Capabilities`, `Migrations` with its batched `LinkRepair`, `Linking`, which keeps the links' meta keys, depths, lock and queries, and `OrderTypes`, which words the order types. A component takes ungated services in its constructor, such as `AdminNotices` or `Assets`, which `Plugin::get_definitions()` provides. Quality's syntax job parses the entry, `uninstall.php` and `Safeguards.php` on PHP 7.4, and `phpstan.safeguards.neon` analyzes the entry and `Safeguards.php` at PHP 7.4 and the oldest WordPress the bootstrap package runs on.
- `models/DWS_Order_Node.php` keeps v1's global class on Composer's classmap: a node wraps an order of a supported type, reads its depth, parent and children from the order's meta once, and saves them back through WC CRUD.
- `includes/` extends `functions.php` with v1's `@api` functions and constants, grouped by topic: v1's settings, order-type and linking APIs (`settings.php`, `post-type.php`, `linking.php`), v1's deprecated root functions and constants (`deprecated.php`) and the slug, name and version getters a peer plugin reads (`metadata.php`). With the entry's `DWS_LOWC_FILE` and `DWS_Order_Node`, these are the plugin's only globals, each tagged `@api`, so other plugins integrate through them, its hooks and WordPress's and WooCommerce's APIs on the names it documents, and never through `src/`.
- `assets/src/` holds the orders list's TypeScript and SCSS, which `npm run build` compiles into `assets/build/`; the framework's `Assets` reads the `*.asset.php` file wp-scripts writes beside each build.

## Data

- **Order links** are three meta keys on each linked order, as v1 stored them: `_dws_lo_depth`, where a root is 0, `_dws_lo_parent` and `_dws_lo_children`, plus `_dws_lo_created_by` on a child the plugin created. WC CRUD writes them to whichever storage WooCommerce uses. Every link reads and rewrites the parent's `_dws_lo_children`, so `dws_lowc_link_orders()` holds the `dws_lowc_linking` option lock while it links, re-reads both orders' meta from the database under it, with WooCommerce's order-tables data caching off for the reads, and waits up to five seconds for another request's link to finish before it returns false. It saves the child first and the parent only once the child's parent reads back, since WooCommerce logs a failed save and carries on; on either refusal `dws_lowc_create_linked_child()` deletes the child it created and returns a `WP_Error`. When an order is deleted for good, its children become the roots of their own trees and their descendants' depths are rewritten, under the same lock.
- **Options** keep v1's keys, `dws-lowc_general_max-depth`, `dws-lowc_general_autocomplete-descendants` and `dws-lowc_plugin_remove-data-uninstall`, as `Options`' constants, whose defaults `DEFAULTS` holds in the form each option stores, and `Options::V1_SETTINGS` maps v1's group and field ids to them. The first migration stores every absent default, and each field's default reads the same entry. Code reads them through `Options`' typed readers, which pass each through v1's validated read: it validates the stored value, falls back to the key's default and applies v1's filters. v1's deprecated API in `includes/settings.php` reads them by v1's field ids the same way.
- **Migrations** are the append-only steps `Migrations::get_steps()` returns, each a protected static of the class or, for bulk work, a final class of its own. The framework's runner runs each pending step once per site on `wp_loaded`, behind a lock, and records the revision reached in `dws_lowc_revision`. The first step stores each setting's default where a site, v1 or new, has none. The second, `LinkRepair`, is batched: it walks every order that stores a parent, 50 to a batch, under the linking lock, and reads and writes the link meta by its literal keys: a child whose parent no longer loads becomes the root of its own tree, a child missing from its parent's children joins them, and a child at another depth than one below its parent moves there with its descendants, repairing what v1's deletions and lost updates left. A step converges from any partial state and throws when a write fails, so a failed step runs again on a later request.
- **The footprint**, `Plugin::FOOTPRINT`, names every kind of data the plugin stores: the `dws_lowc_` and `dws-lowc_` option prefixes, the `_dws_lo_` order meta on both storages, v1's version and notice rows, user meta, network options, the capabilities, scheduled hooks and Action Scheduler groups. Freemius's `fs_` rows from v1 stay, since they belong to Freemius.
- **Deactivation** unschedules every hook in the footprint's `cron_hooks` and `as_hooks` on the current site.
- **Uninstall** runs `uninstall.php`, which calls the framework's uninstall engine over the footprint, with WooCommerce's order meta types, on every site whose `dws-lowc_plugin_remove-data-uninstall` setting consents, as a v1 site's consent carries over; a site that never consented keeps its data. Below the floors or with an incomplete build, a web request deletes the files, keeps the data and logs why, while WP-CLI fails and keeps both for a rerun.

## Prefixing and distribution

Every development install runs php-scoper through wordpress-configs, which copies the framework, PHP-DI and their dependencies into `vendor-prefixed/` under `DeepWebSolutions\LinkedOrders\Scoped\`, so each plugin carries its own copy and never meets another plugin's. The release workflow builds `linked-orders-for-woocommerce.zip` from a production install, checks it with Plugin Check, the archive and header checks, activates it on a site and runs the end-to-end suite against it. A pull request rehearses the same build without publishing. A tag publishes a GitHub release and deploys the zip to the wordpress.org directory, which offers it to sites; `composer changelog:write` turns `changelog/` into `CHANGELOG.md` and copies its versions into `readme.txt`. The listing's banners, icons and screenshots stay in the directory's SVN, since the plugin ships no `.wordpress-org/`.
