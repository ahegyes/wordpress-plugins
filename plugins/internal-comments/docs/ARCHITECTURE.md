# Architecture

This document describes how the plugin loads, boots, stores its data and leaves a site, and where each kind of code lives.

## Loading

`internal-comments.php` is the only file WordPress includes, and it parses on PHP 7.4 so that a site below the floors gets a notice instead of a fatal error:

1. It defines `DWS_IC_FILE`; translations come from wordpress.org's language packs, which WordPress loads just in time.
2. It requires `Safeguards.php` and registers its safeguard, which refuses WordPress's own actions on internal comments until the booted plugin relaxes it, so it holds on any runtime that parses the plugin: below the floors, on a partial deploy and when the boot fails.
3. Inside one `try`, it requires `vendor-prefixed/ahegyes/wp-framework-bootstrap/load.php`, registers the GitHub updater, which stays inert because the entry file has no `Update URI` header, then checks the `Requires PHP` and `Requires at least` headers. The updater comes first, so a release that lowers the floors still reaches a site below them. On a site below a floor, WordPress's own notice shows and nothing past the safeguards loads.
4. It requires the autoloader and `functions.php` once the meta box's built script is present. A missing bootstrap package, build or required file throws, which local and development environments rethrow, while every other environment shows users who can activate plugins a notice that the build is incomplete.

`functions.php` defines the `@api` `dws_ic_plugin()` accessor, requires every `includes/*.php` in name order except those whose names start with `_`, then, from static closures, boots the plugin on `plugins_loaded` at priority 15, after WooCommerce and Action Scheduler have loaded where they are active, declares the plugin compatible with WooCommerce's order tables, relays the framework's boot hooks to v1's `dws_ic_initialized` and `dws_ic_initialization_failure` and registers the deactivation callback.

## Booting

`src/Plugin.php` is the composition root. Its constructor builds the plugin's identity from its entry file, slug and prefix, then the logger, the scheduler and the framework's `PluginBoot`, which each take the identity, and `PluginBoot` runs the composition and reports its outcome:

- The scheduler, on WP-Cron, registers its hooks first, so the migration runner's scheduled hook keeps running.
- The migration runner registers, and runs pending steps on `wp_loaded` and from its scheduled hook.
- The kernel builds each class in `Plugin::COMPONENTS` through a PHP-DI container and calls its `register_hooks()`.
- `CapabilityGrants` gives v1's twelve capabilities to administrators, and the five that post, see and mark comments private to editors, authors, contributors and shop managers, on `wp_loaded`, once per change of the declaration or the roles.
- Once every component has registered, the boot is `booted` and `internal_comments/boot/succeeded` fires. A throw anywhere in the composition makes it `failed`: `internal_comments/boot/failed` fires, the failure is logged, and administrators see a notice, while local and development environments rethrow it.

WooCommerce is optional: without it, every feature but the order screens and the orders list works. The request that activates the plugin does not boot it, because WordPress includes the plugin's file after `plugins_loaded`; its screens and migrations first run on the next request.

## Where code lives

- `src/` holds the plugin's classes, each final and named for its concept. The components implement the framework's `ComponentInterface` and add their hooks in `register_hooks()`: `Settings` declares v1's settings page to the framework's `OptionsPage`; `Permissions` maps the meta capabilities and holds core's REST API and XML-RPC to them, which otherwise let moderators and a comment's author past; `Comments` keeps internal comments under their status, records their revisions and holds their type, status and private meta; `MetaBox` adds the meta box to posts and orders of the selected types; `RestRoutes` registers the routes the meta box and quick view call; `ListColumn` adds the list column and its quick view, `CommentsScreen` the Comments screen's view and `CommentEditScreen` the edit screen's revisions and privacy; `PersonalData` adds internal comments to WordPress's personal data export and erasure, whose own comment exporter and eraser leave them out, anonymizing each comment's author as WordPress does and keeping its text. Each checks the user's capabilities in its callbacks. The classes that register no hooks are `Options`, `Capabilities`, `Migrations` with its batched `CommentStatusMove`, and `CommentsList`, which loads the templates the meta box prints and the routes answer with. A component takes ungated services in its constructor, such as `AdminNotices` or `Assets`, which `Plugin::get_definitions()` provides. Quality's syntax job parses the entry, `uninstall.php` and `Safeguards.php` on PHP 7.4, and `phpstan.safeguards.neon` analyzes the entry and `Safeguards.php` at PHP 7.4 and the oldest WordPress the bootstrap package runs on.
- `models/DWS_Internal_Comment.php` keeps v1's global class on Composer's classmap: it wraps an internal comment, passes reads and calls to it, and answers whether a user may see, edit or trash it.
- `templates/admin/` holds v1-style views: `html-comments-list.php`, `html-comment.php`, which loads itself for each reply, and `html-comment-form.php`, with the meta box's hooks. Each reads only its `$args` and assigns no WordPress global, since `load_template()` declares several in its scope; the meta box's shell, the list column, the revisions box and the privacy field print from their classes.
- `includes/` extends `functions.php` with v1's `@api` functions and constants, grouped by topic: v1's settings and comment APIs (`settings.php`, `comments.php`), v1's deprecated root functions and constants (`deprecated.php`) and the slug, name and version getters a peer plugin reads (`metadata.php`). With the entry's `DWS_IC_FILE` and `DWS_Internal_Comment`, these are the plugin's only globals, each tagged `@api`, so other plugins integrate through them, its hooks and WordPress's APIs on the names it documents, and never through `src/`.
- `assets/src/` holds the meta box's and quick view's TypeScript and SCSS, whose shared comment-list rules live in the `_comments.scss` partial, which `npm run build` compiles into `assets/build/`; the framework's `Assets` reads the `*.asset.php` file wp-scripts writes beside each build.

## Data

- **Internal comments** are comments of v1's `dws_internal` type, stored under the `dws_internal` status. WordPress's comment queries, counts, feeds and REST API include only the statuses they name, so they leave internal comments out without the plugin's help, active or not. `Comments` puts back under the status any internal comment that WordPress or another plugin stores, approves, holds, marks spam or restores under another, announcing each move back through `wp_transition_comment_status()` after WordPress's own announcement so status-following caches such as WooCommerce's comment counts stay right, and keeps every field but the text as stored when one is updated. It also leaves their type out of every comment query and feed that names neither the type nor the status, through the query's WHERE clause, which keeps WooCommerce's exclusion of product reviews working, so the comments v1 stored approved stay hidden until the migration moves them, and so does a comment whose move back under the status failed, which no one is mailed about. The Comments screen lists them only under their own view. A post's comments on a trashed post are read from what WordPress recorded when it trashed the post.
- **Comment meta** keeps v1's keys: `dws_ic_is_private`, `yes` on a comment marked private, which only its author changes, and only before anyone replies when it turns private; and, per change to a comment's text, `_dws_ic_change_id` with `_dws_ic_previous_content_{id}`, `_dws_ic_changed_by_{id}` and `_dws_ic_changed_time_{id}`.
- **Options** keep each setting in a row of its own, `dws_ic_post_types`, `dws_ic_private_comments_enabled` and `dws_ic_delete_data`, named by `Options`' constants, whose defaults `DEFAULTS` holds in the form each option stores, and `Options::V1_SETTINGS` maps each of v1's fields to its row. A migration step copies v1's `dws-internal-comments_general` and `dws-internal-comments_plugin` rows into them and leaves v1's rows for a rollback. Code reads them through `Options`' typed readers, which fall back to each default; private comments pass v1's group filter, as v1's read did, and the selected post types are read raw, also as v1 read them, so a post type that registers late stays selected. v1's deprecated API in `includes/settings.php` reads them by v1's field ids, validated, through v1's filters.
- **Migrations** are the append-only steps `Migrations::get_steps()` returns, each a protected static of the class or, for bulk work, a final class of its own. The framework's runner runs each pending step once per site, behind a lock, and records the revision reached in `dws_ic_revision`. The first step copies each field of v1's settings rows into its row where the site stores none, and the second stores each default still absent; neither overwrites a stored row. The third, `CommentStatusMove`, is batched, so it runs only from the runner's scheduled hook: it walks the comments table by id window, moves the internal comments v1 stored approved, pending or as spam to the status and recounts their posts, keeping its position in `dws_ic_v1_comments_cursor` until the walk ends. A step converges from any partial state and throws when a write fails, so a failed step runs again on a later request.
- **The footprint**, `Plugin::FOOTPRINT`, names every kind of data the plugin stores: the `dws_ic_` and `dws-internal-comments_` option prefixes, the `dws_internal` comments with their meta, v1's version and notice rows, user meta, network options, the capabilities, scheduled hooks and Action Scheduler groups. Freemius's `fs_` rows from v1 stay, since they belong to Freemius.
- **Deactivation** unschedules every hook in the footprint's `cron_hooks` and `as_hooks` on the current site. Internal comments stay hidden, since their status hides them.
- **Uninstall** runs `uninstall.php`, which calls the framework's uninstall engine over the footprint on every site whose `dws_ic_delete_data` setting consents, which the first migration step copies from v1's; a site that never consented, or never ran the update while the plugin was active, keeps its data. Below the floors or with an incomplete build, a web request deletes the files, keeps the data and logs why, while WP-CLI fails and keeps both for a rerun.

## Prefixing and distribution

Every development install runs php-scoper through wordpress-configs, which copies the framework, PHP-DI and their dependencies into `vendor-prefixed/` under `DeepWebSolutions\InternalComments\Scoped\`, so each plugin carries its own copy and never meets another plugin's. The release workflow builds `internal-comments.zip` from a production install, checks it with Plugin Check, the archive and header checks, activates it on a site and runs the end-to-end suite against it. A pull request rehearses the same build without publishing. A tag publishes a GitHub release and deploys the zip to the wordpress.org directory, which offers it to sites; `composer changelog:write` turns `changelog/` into `CHANGELOG.md` and copies its versions into `readme.txt`. The listing's banners, icons and screenshots stay in the directory's SVN, since the plugin ships no `.wordpress-org/`.
