# wp-internal-comments

Internal Comments, the v2 port of the wordpress.org plugin of that name, built on four wp-framework packages (`ahegyes/wp-framework-{bootstrap,shared,core,settings}`) from the plugin template, with WooCommerce as an optional host for orders. It ships its own copy of the framework, PHP-DI and their dependencies, prefixed under `DeepWebSolutions\InternalComments\Scoped` by php-scoper through wordpress-configs into `vendor-prefixed/` on every development install. Its architecture follows the framework's conventions 1–10 in [wordpress-framework's AGENTS.md](https://github.com/ahegyes/wordpress-framework/blob/trunk/AGENTS.md); this file covers what is particular to the plugin. `docs/ARCHITECTURE.md` describes the boot and the data, `tests/README.md` the suites, and the template's [recipes](https://github.com/ahegyes/wordpress-plugin-template/blob/trunk/docs/recipes.md) the common changes, under the template's `dws_tpl` prefix.

v1 sites upgrade in place, so the port keeps v1's comment type, capabilities, comment meta, settings page and helper API, copies each setting from v1's rows to a row of its own, and fires each v1 hook, deprecated, before its v2 name.

## Layout

```

Safeguards.php               the safeguards that refuse WordPress's own actions on internal comments until the booted plugin relaxes them, and WooCommerce's note routes and core's listings, which the entry requires before the floor check

src/                         the plugin's classes, each named for its concept

├── CommentsList.php         the loader of the templates the meta box prints and the REST routes answer with
├── MetaBox.php              the meta box on the edit screens of posts and orders of the selected types
├── RestRoutes.php           the internal-comments/v1 routes the meta box and the quick view use
├── ListColumn.php           the posts and orders list column with its quick view
├── CommentsScreen.php       the Comments screen's view of internal comments, and their place in its other views, counts and actions

includes/                    v1's @api functions and constants, grouped by topic, loaded in name order, _-prefixed files skipped
├── settings.php             v1's deprecated settings API, the raw and validated reads by v1 field id and group, and the readers of the selected post types and of private comments
```

## Commands

```sh
composer packages-install    # dependencies, then php-scoper into vendor-prefixed/
composer test:unit
composer test:integration    # starts .wp-env.tests.json, then runs test:integration:run, which builds the scripts first
composer test:integration:multisite  # starts .wp-env.multisite.json, then runs the Integration suite's multisite group, which the default run skips
composer quality-check       # manifest and changelog validation, PHPCS (both profiles), PHPStan (both profiles), Unit and Integration
composer changelog:add       # stages an entry in changelog/, which the release step in the monorepo's CONTRIBUTING.md writes
npm run setup                # both installs, the scripts' build, then the development site
npm run build                # the meta box's and quick view's assets through the local wp-scripts; npm run start watches them in a POSIX shell
npm run lint:scripts         # ESLint, beside lint:styles (Stylelint) and lint:types (tsc)
npm run test:e2e             # Playwright on .wp-env.tests.json, starting it if needed; the scripts must be built
```

Run wp-scripts only through the npm scripts or `node_modules/.bin/wp-scripts`: `npx wp-scripts` can install an unrelated package of that name.

## Environments

- `.wp-env.json`: development, as `local`, on port 8824, behind `npm run setup` and `wp-env:*`. The framework rethrows boot and migration failures there.
- `.wp-env.tests.json`: Integration and end to end, as `production`, on port 8825, behind `wp-env:tests:*`, `composer test:integration` and `npm run test:e2e`. The end-to-end suite deactivates and reactivates WooCommerce there.
- `.wp-env.multisite.json`: a network with WooCommerce and the plugin network-activated, as `production`, on port 8829, behind `wp-env:multisite:*` and `composer test:integration:multisite`, for the Integration suite's `multisite` group.

Each runs PHP 8.5 with WooCommerce from `vendor/` and its order tables on; CI runs Integration and end to end on every WordPress branch from the entry's `Requires at least` up, and nightly on WordPress trunk.

## Conventions

1. **Placement and surface.** The global namespace holds only the plugin's contract, each global `@api`, which `GlobalsTest` checks, and tested: the entry's `DWS_IC_FILE`, the functions and constants `functions.php` and `includes/` declare, among them v1's helper API and the accessor, whose composition root is internal, and `DWS_Internal_Comment`, which keeps v1's global name in `models/`; `functions.php` registers its hooks as static closures. The globals load before the boot, so they stay defined whether or not it succeeds, and until it has, the `src/` code an `@api` function or the model calls reaches nothing the boot checks, such as WooCommerce, and does something neutral in its place. Integrators touch only those globals, the plugin's hooks and WordPress's and WooCommerce's APIs on the contract's literal names, never `src/` or `Safeguards.php`. A symbol enters without a named caller when it exposes a noun or verb the plugin's screens give an admin, a decision the plugin makes, an event when it changes its data or the inverse of an operation it exposes; when the literal's direct use would need something the plugin enforces, such as a lock, a per-site key, a list's read-modify-write or paired keys; when the plugin's own code runs the same implementation, an exception taking the owner's ruling; and when its signature holds only scalars, WordPress and WooCommerce types and the plugin's models. One model serves each noun, a new capability of a concept being a method on its model; an open set of interchangeable behaviours is a `models/` interface behind register, get-one and get-all functions, never a function per variant; a setting gets no reader, and the decision it feeds is exposed instead; each state change gets an action; and nothing lock-bound or php-scoper-typed enters. Every other symbol is a member of a final class in `src/` named for its concept, `protected` wherever only its class uses it: the composition root, which holds the footprint, a component, `Options`, `Migrations` or another class that registers no hooks, such as `CommentsList`. No namespace or folder is named "Internal". Container definitions are composition and stay in `Plugin::get_definitions()`; a component takes a service such as `Assets` by constructor.
2. **Request context.** `is_admin()` is false on REST requests and true in admin-ajax ones, so an admin-only feature decides the request context in its callbacks, never in `should_load()`.
3. **Add-ons.** An add-on extends a base plugin only through the base plugin's contract. It reads a template-built base plugin's slug, name and version through that plugin's `{prefix}_get_plugin_*()` getters, asks its decision functions, such as this plugin's `dws_ic_is_private_comment()`, and otherwise reads its options through `get_option()` on their contract names. It calls the base plugin's functions no earlier than `plugins_loaded`, or than the hook a function's docblock names, since the add-on may load first, and behind `function_exists()`, since a base plugin below its floors or with a partial build may stay active without defining them, and registers its extensions on the base plugin's `{root}/boot/succeeded`, which fires only once that plugin has booted, adding that callback before `plugins_loaded` reaches priority 15, where the base plugin boots, such as from its `functions.php`.
4. **Request reads.** An integer or boolean is read as `filter_var( wp_unslash( $_POST['key'] ?? '' ), FILTER_VALIDATE_INT, FILTER_NULL_ON_FAILURE ) ?? $default` (`FILTER_VALIDATE_BOOL` for a boolean, where an absent key reads false, as an unchecked checkbox posts nothing), and a string through an `is_string()` guard and the field's sanitizer; never `filter_input()`, the `default` filter option or a cast on request input. A REST route declares each parameter's type and sanitizer in its `args`.
5. **Options and data.** Each setting is one autoloaded option, its key on `Options` and its default in stored form in `DEFAULTS`, which the seeding step stores after the copy of v1's settings, a release that adds settings seeds again, and its field reads. Outside the safeguards and the migration steps, settings are read only through `Options`' typed readers, which pass private comments through v1's group filter and read the post types raw, as v1 did; v1's API in `includes/settings.php` is deprecated, and the post types' and private comments' readers there delegate to `Options`. Each setting has a row of its own under `dws_ic_`, while v1's `dws-internal-comments_` rows stay as they were for one major; v1's comments keep their `dws_internal` type and `dws_ic_is_private` and `_dws_ic_` meta; anything new lives under `dws_ic_`, or `_dws_ic_` for hidden meta. The footprint covers those prefixes and v1's other rows by name. Migration steps are append-only: a step converges from any partial state, verifies its writes and throws when one fails; bulk work is a batched step, a final class of its own that runs only from the runner's scheduled hook. A step names each stored name it touches, such as an option or meta key or the comment type, and each default as a literal and reads stored rows directly, never through `Options`, a reader or a constant another class declares, so a later rename leaves what it does as it shipped; the seeding step alone reads `Options::DEFAULTS`.
6. **Internal status.** An internal comment is stored under the `dws_internal` status, which keeps it out of WordPress's queries, counts, feeds and REST API without the plugin's help, so no code stores one under another status, and a query that lists them names the status. `Comments` puts back any that WordPress or another plugin moves, announcing the move as a status change after WordPress announces its own, so caches that follow status changes, such as WooCommerce's comment counts, end where the comment is; the migration's bulk move resets WooCommerce's counts instead. It also leaves the type out of every comment query and feed that names neither it nor the status, through the WHERE clause, since WooCommerce leaves product reviews out of no query that names types to leave out, so the comments v1 stored approved stay hidden until the migration moves them, and so does one whose move back fails, of which no one is mailed. Every check of what a user may do with one goes through the `see_`, `edit_` and `trash_dws_internal_comment` meta capabilities.
7. **Order storage.** Order code takes ids WooCommerce resolves in either storage, through `Comments::get_post_type()` and `edit_post`, which WooCommerce maps for orders, and WooCommerce's screen ids and list hooks, never the posts table; every Integration row whose outcome the order storage can change runs on all four storages through `OrderStorageTrait`.
8. **v1 hooks.** A hook v1 fired keeps its v1 literal, fired first through `apply_filters_deprecated()` or `do_action_deprecated()` with `'2.0.0'` and the v2 name, then the v2 name. v1's settings value filters have no v2 name: they name the option's own `option_{$option}` filter.
9. **Safeguards.** `Safeguards.php` holds five: at the last priority of `map_meta_cap`, one refuses `edit_comment` on an internal comment, which WordPress checks before it edits, moderates, trashes or deletes a comment, and on `rest_request_before_callbacks` another refuses core's REST comments controller an internal comment, which it updates and deletes for a user who moderates comments without asking `edit_comment`, both until `Permissions` relaxes them through `internal_comments/core_comment_actions/should_restrict` once the plugin has booted; the REST one also answers WooCommerce's note routes on an internal comment as a missing note, a third refuses WooCommerce's note deletion one, and two leave internal comments out of core's REST listing and XML-RPC's, all whether or not the plugin has booted. A safeguard added there follows the template's safeguard recipe: `register()` hooks it as a static closure, which no code can remove by name, and it relaxes only through its own filter, through the protected `is_relaxed()`. The entry requires the class before the floor check, so it parses on PHP 7.4 and calls only WordPress APIs present at the oldest WordPress the bootstrap package runs on, or guards them, which `phpstan.safeguards.neon` checks.

## Contract

The plugin's contract is the elements tagged `@api`, the hooks it fires, its REST routes and the names it stores, checks or documents: its option, comment meta and capability names and its comment type and status. Each stored or checked name is written whole as a constant on the `src/` class that owns it, never as a global constant or an enum, and its literal is the contract. Breaking the contract ships as the next major. Every other function, constant and class, `src/` included, is internal and changes in any release.

## Style

- Every PHP file opens with `<?php declare( strict_types=1 );`, uses `array()`, `final` classes, `protected` over `private` and `#[\Override]` on overrides, and groups class members in `// region NAME` blocks outside `tests/`.
- Docblocks open with one third-person sentence naming the role, such as "Returns …", plus a second paragraph only for a non-obvious why; property and constant docblocks open with "The …", constructors read "Constructor.", overrides read `{@inheritDoc}`. Every other function docblock ends with `@return`, `@return  void` included; tag values align at column 10, each `@param` stays on one line, and `@throws` reads "Thrown when …". Every public `do_action()` and `apply_filters()` carries a hook docblock.
- A hook the plugin fires is named `internal_comments/area/name`, with `/` between levels and `_` between words, as the framework names its own, and its last level says what kind of hook it is: a past participle for an event (`internal_comments/boot/succeeded`), `before_` or `after_` for a position (`internal_comments/internal_comment/before_insert`), an imperative for a scheduled hook, a predicate (`is_`, `has_`, `can_`, `should_`) for a boolean filter, and the noun of the value for any other filter, plural for a list (`internal_comments/meta_box/comment_classes`).
- An element v1 had keeps v1's `@since`, and its `@version` names the release that last changed it.
- Inline comments state a non-obvious why in one capitalized sentence, and every file describes the present, never the change; a `phpcs:ignore` names its sniff and gives a reason.
- Markdown keeps one line per paragraph, sentence-case headings and an impersonal, present-tense voice.
- Commit subjects are capitalized imperatives of 72 characters or fewer, with no `type(scope):` prefix and no trailing period. The body says what was wrong and why before what changed, and an agent-assisted commit ends with `Assisted-by: <agent>:<model-id>`, never `Co-Authored-By`.

## Limitations

- Integration and end to end share the tests site, so a row that changes shared data in a separate process flushes the parent's object cache.
- The end-to-end suite runs on the order tables only, as the tests site stores orders; the Integration rows cover the posts storage.
- A site that returns to 1.2.4 after the upgrade stores its new internal comments approved, and the migration that moved v1's comments does not run again on the next upgrade, so those comments stay out of the meta box and in their post's comment count until moved by hand.
- Core's comment edit screen hides an internal comment's author, status, date and parent (`#namediv`, `#comment-status`, `.misc-pub-curtime`, `.misc-pub-reply-to`) through a style on core's element ids and classes, so a core release that renames them shows those fields again, and saving still keeps them as stored; the Comments screen hides an order's View link through core's `.comments-view-item-link` the same way.
- A role given the Comments screen's list capability without `see_private_dws_internal_comments`, or without access to edit every post, can see a page of internal comments run short of its size, and view counts above the rows listed, because the comments it may not see are dropped after the query, which cannot follow a private comment's chain of owners.
- A comment turns private only before anyone replies to it, so every reply under a private comment comes from a user who could see it; code that adds the flag with `add_comment_meta()` where none is stored passes neither this rule nor the author rule, which keeps imports of private comments working. A thread that 1.2.4 made private after others had replied still loses part of its privacy when its first comment is deleted permanently: the replies become private under their own authors, who then also see the replies beneath them that the deleted comment's privacy hid from them.
- A private comment reads as ordinary between WordPress's insert of its row and of its meta, and a reply loses the privacy it took from a comment deleted for good when the write that carries it over fails while the deletion succeeds.
- Restoring an internal comment restores every reply in the Trash under it, a reply trashed on its own before it included, as 1.2.4 did.
- Core's comment edit screen stores whatever comment meta its form posts, so a user who may edit an internal comment can also write its revision records.
- Core's comment edit screen opens for an internal comment only to a user who can both edit and trash it, because core trashes, deletes, restores and moderates on the same `edit_comment` check; a role that can only edit edits in the meta box.
- The bundled GitHub updater ships inert, since the entry file has no `Update URI`, and wordpress.org's reviewers may ask to remove it.
